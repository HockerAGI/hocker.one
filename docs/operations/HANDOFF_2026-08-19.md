## 5. Errores que NO deben repetirse

1. **No usar un Preview READY de un SHA anterior** como evidencia de un head nuevo, aunque el árbol parezca parecido.
2. **No crear commits vacíos/dummy para reintentar Vercel** si el proveedor permite Redeploy; cada commit genera ruido, deployments y potencial CI.
3. **No confundir rate limit de proveedor con fallo de código.** Primero inspeccionar status y build logs.
4. **No permitir batch eval con snapshot parcial.** La incertidumbre debe detener efectos/costo.
5. **No insertar evals aprobados directamente por SQL/service role** ni fabricar una cookie/sesión AAL2.
6. **No re-enrolar TOTP si ya existe un factor verificado.** El flujo correcto es challenge + verify para elevar la sesión.
7. **No ejecutar todas las AGIs en paralelo.** Mantener secuencial/resumible hasta tener evidencia de que cambiarlo no rompe límites, costes o persistencia.
8. **No habilitar `allow_actions` para “pasar” certificación.** El boundary guarded es parte de la certificación.
9. **No silenciar Supabase Advisor con revocaciones masivas.** Las excepciones GraphQL/RPC se revisan por contrato/objeto.
10. **No rehacer Railway/NOVA fallback.** Verificar primero la implementación existente, exact revision, `/health/ready`, logs y E2E.
11. **No convertir tool annotations MCP en autorización.** Son metadata/hints; Owner Gate/policies siguen siendo autoridad.
12. **No migrar de framework agentic durante cierre sólo por novedad.** Adoptar patrones probados primero; un cambio de SDK exige ADR + regression eval + rollback.
13. **No duplicar el mismo estado en cinco documentos.** Este handoff contiene detalle; los demás documentos sólo deben referenciarlo o registrar un delta.

## 6. GitHub Actions / FinOps de CI

Dato oficial vigente: los **standard GitHub-hosted runners son gratuitos y sin límite de minutos para repositorios públicos**. Los repositorios privados consumen la asignación de minutos del owner/organización; larger runners se cobran incluso en repos públicos.

Implicación HOCKER:

- `hocker.one` es público y usa standard runner; su CI no debe confundirse con el consumo de minutos de los repos privados.
- La restricción global comunicada por Owner sigue siendo real para los repos privados (`hocker.ads`, `chido.lab`, `chido.games`, `punto.g`, etc.): minimizar runs allí.
- Cambios sólo Markdown deben permanecer fuera del CI general cuando `paths-ignore` ya lo permita y cuando ese check no sea required de forma que quede Pending.
- Agrupar documentación en un solo commit en vez de múltiples micro-commits.
- No usar `[skip ci]` indiscriminadamente: un required check omitido puede quedar Pending y bloquear merge.
- Para código: un RED TDD enfocado + un GREEN candidate + gate final; evitar commits intermedios innecesarios.
- Donde aplique, `concurrency.cancel-in-progress`, cache de dependencias y path filters reducen desperdicio; cambiar workflows también es un cambio material y no debe hacerse sólo por optimización cosmética.
- No sustituir CI de seguridad/release requerido por ahorro de minutos.

## 7. Investigación oficial y repos externos — decisiones para la siguiente fase

### Vercel

Documentación revisada: Limits, Project Settings / Ignored Build Step y Troubleshooting Build Errors.

Hallazgos operativos:

- Hobby documenta 100 deployments por ventana diaria y 1 concurrent build; alcanzar el límite puede requerir esperar a que la ventana se libere.
- `Redeploy` existe desde el Dashboard y puede reutilizar el mismo commit sin un commit artificial.
- `Ignored Build Step` puede evitar builds no útiles, pero debe diseñarse para no bloquear Preview/production evidence que sí sea obligatoria.
- Build Logs, Resources y Source son superficies de evidencia; `READY` por sí solo no sustituye smoke/runtime review en cambios funcionales.

### Supabase MFA

Documentación revisada: MFA TOTP y `getAuthenticatorAssuranceLevel()`.

Contrato oficial relevante:

- `aal1` = primer factor;
- `aal2` = primer factor + MFA;
- `currentLevel=aal1` y `nextLevel=aal2` significa que ya existe un factor enrolado y falta challenge/verify;
- TOTP MFA está disponible en todos los proyectos; no confundirlo con Leaked Password Protection;
- en SSR, una sesión que necesita elevar AAL debería dirigirse al paso MFA en vez de interpretarse como identidad inválida.

PR #230 ya sigue este patrón; no rediseñarlo antes de la ceremonia.

### OpenAI Agents SDK — referencia, no migración autorizada

Repositorio oficial revisado: `openai/openai-agents-js`.

Patrones aprovechables:

- tool approval pausa el run y conserva un `RunState` resumible;
- una decisión de approval queda ligada a tool/call identity y no debe solicitarse de nuevo al reanudar;
- guardrails deben ejecutarse cerca del efecto, incluso otra vez después de una aprobación si el contexto pudo cambiar;
- state serializado permite esperas humanas largas sin mantener servidor vivo;
- tracing cubre generaciones, tools, handoffs y guardrails, pero los datos sensibles deben tratarse explícitamente.

Aplicación a HOCKER: mantener el diseño actual resumible/server-derived y usar estos patrones como benchmark. No reemplazar el runtime antes del cierre de #230.

### MCP

Repositorio oficial revisado: `modelcontextprotocol/typescript-sdk`; la línea v2 estable implementa la especificación MCP `2026-07-28`.

La revisión 2026-07-28 introduce cambios de transporte/lifecycle relevantes, incluido core stateless y cambios incompatibles respecto de 2025. El canon HOCKER 2026.08 aún referencia MCP 2025-11-25; esto es drift documental/tecnológico, **no una orden de migración inmediata**.

Decisión: abrir una fase/ADR de compatibilidad MCP v2 después de Core closure. Primero inventariar uso actual de v1/2025 contracts, adapters y consumers. Mantener Owner Gate como autorización real; metadata/annotations nunca sustituyen policy.

### Vercel AI SDK — referencia de riesgo

Repositorio oficial revisado: `vercel/ai`. Issues recientes de 2026 muestran que approval/resume ha tenido edge cases reales, incluidos signatures de approvals al reanudar. Son señales para pruebas, no evidencia de que HOCKER tenga esos bugs.

Decisión: cualquier futura adopción de approval primitives de AI SDK debe probar approve/reject/resume/retry/idempotency/signature/timeout antes de producción. No migrar PR #230 a otro primitive durante su gate final.
